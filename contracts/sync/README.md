# Sync Contracts

Xueqing uses Local-first Command Sync, not a general CRDT.

The sync contract defines durable command intent, operation-result lookup, server change cursor, authorization/scope version, conflict/error envelopes, purge instructions and retry classes.

## Durable Outbox envelope

Minimum durable fields:

- `operation_id`: client-generated stable UUID. The same user intent keeps the same value across timeout, process restart and retry.
- `command_type`: server command name.
- `aggregate_id`: optional target aggregate identifier.
- `scope_key`: local authorization/business scope binding.
- `expected_version`: optional optimistic-concurrency version.
- `freshness_token`: optional relationship/authority freshness binding.
- `payload_json`: exact command payload.
- `created_at_client_utc`: diagnostic client timestamp only.
- `attempt_count`: number of claimed send attempts.
- `queue_status`: `pending | retry | in_flight | acknowledged | dead_letter`.
- retry/error metadata and server receipt where applicable.

The local SQLite implementation also owns a monotonic `local_sequence` generated by the database. Local queue ordering uses this sequence, never wall-clock timestamps.

## Identity and retry rules

`operation_id` is a durable identity, not a request nonce. Enqueuing the same `operation_id` with the same semantic envelope is idempotent. Reusing it for a different command, target, version/freshness binding or payload is a fatal local collision.

A sender claims one ready item with a finite local lease. While the lease is active, another local worker must not claim that item. If the process dies, the lease expires and the same operation becomes claimable again with the same `operation_id`.

A stale worker may not acknowledge, retry or dead-letter an operation after another worker has reclaimed it. State mutation must present the currently owned lease id.

A crash after the server commits but before the client records acknowledgement is resolved by retrying the same `operation_id`; the server command layer must return the already-committed result/receipt instead of executing a second business mutation.

`acknowledged` and `dead_letter` are terminal local queue states.

## Pull side

The pull side will use a server-issued monotonic/opaque change cursor plus authorization/scope versioning and purge instructions. Realtime may improve freshness, but it is never the correctness mechanism.

Never use wall-clock `updated_at` alone as a causal ordering mechanism.
